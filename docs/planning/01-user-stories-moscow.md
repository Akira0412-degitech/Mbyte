# mbyte 拡張計画 — User Story & MoSCoW優先度

作成日: 2026-11-12
対象: Go言語への移植 + 既存の未実装4ギャップの解消

---

## 背景: なぜこの5つのEPICか

市場調査で「insert/replaceの明示的分離」と「署名境界検出」は既存ツール(Detect It Easy, ImHex, Web型チェッカー)に無い差別化点として既に実装済みと確認した。
一方で以下4点は未実装のまま残っている。

1. **プリセット非対称** — `detect_format`はELF/PE/7z/RAR/gzip/Javaクラスまで検出できるのに、`insert`/`replace`で使えるプリセットは6種類(png/gif89a/gif87a/jpeg/pdf/zip)のみ。検出できるのに偽装できない。
2. **diffプレビュー + 整合性チェック未実装** — 実行前の確認がなく、実行後も先頭16バイトのhexdumpのみ。`replace`で失われるバイト数や、ペイロード部分が本当に無傷かのハッシュ比較がない。
3. **バッチ処理未実装** — 1ファイル×1操作のみ。複数ファイル、複数プリセットへの一括適用ができない。
4. **polyglot二重有効性チェック未実装** — 先頭バイトの一致だけで「本当にそのフォーマットとしてパースできるか」(PNGのchunk構造、ZIPのEOCD、JPEGのEOIマーカー等)は検証していない。

Go移植は、4のpolyglot検証を`image/png` `image/jpeg` `image/gif` `archive/zip` `debug/elf` `debug/pe`などの標準ライブラリで外部依存なしに実現できるという直接的なメリットがあるため、EPIC-0として他の4つより先に土台を作る。

---

## EPIC一覧

| EPIC | 名称 | 概要 |
|---|---|---|
| EPIC-0 | Go移植 | 現行Python実装(core/cli/presets)をGoに移植し、単一バイナリ配布可能にする |
| EPIC-1 | シグネチャプリセット拡充 | 検出対応フォーマット全てをinsert/replaceでも使えるようにする |
| EPIC-2 | diffプレビュー + 整合性チェック | 実行前確認 + ペイロードハッシュ比較による安全性の可視化 |
| EPIC-3 | バッチ処理 | 複数ファイル・複数プリセットへの一括適用 |
| EPIC-4 | polyglot構造検証 | 署名一致だけでなく、対象フォーマットとして実際にパース可能かを検証 |

---

## User Stories

### EPIC-0: Go移植

**US-0.1**
As a 開発者,
I want 現行の`core.py`(署名リスト・hex解析・insert/replace・境界検出)をGoパッケージとして移植したい,
So that 以降の全機能をGo上に構築でき、単一バイナリで配布できる。
- 完了条件: `mbyte insert`/`mbyte replace --raw`がGo版で既存Pythonテスト(`tests/test_core.py`)と同じ入出力を返す。

**US-0.2**
As a 開発者,
I want CLI層(`cli.py`のサブコマンド構成・`--preset`/`--hex`排他・`--force`・`--list-presets`)をGoのCLIライブラリ(cobra等)で再現したい,
So that 既存ユーザーが覚えた操作感を変えずに移行できる。
- 完了条件: 既存README記載の全コマンド例がGo版で同じ出力(hexdump/detected format含む)を返す。

**US-0.3**
As a 開発者,
I want 既存のPythonユニットテストと同等のテストケースをGoの`testing`パッケージに移植したい,
So that 移植によるリグレッションを防げる。
- 完了条件: 正常系(insert/replace)・異常系(不正hex/short replace/ファイル不存在/プリセット不明/署名未検出)が全てGoテストでカバーされる。

---

### EPIC-1: シグネチャプリセット拡充

**US-1.1**
As a CTF問題作成者,
I want `detect_format`が認識できる全フォーマット(ELF, PE, gzip, 7z, RAR, Javaクラス含む)をinsert/replaceのプリセットとしても使いたい,
So that 検出できるのに偽装できないという非対称を解消し、画像・PDF・ZIP以外のファイルタイプでも学習できる。
- 完了条件: `--list-presets`に14種類以上が表示され、全て`insert`/`replace`で動作する。

**US-1.2**
As a 開発者,
I want シグネチャ定義(検出用・プリセット用)を1つのデータソースに統一したい,
So that 検出リストとプリセットリストが将来また食い違う(非対称が再発する)のを防ぐ。
- 完了条件: `_SIGNATURES`相当のテーブルが単一の構造体スライスとなり、検出とinsert/replace双方がそこから導出される。

**US-1.3**
As a 上級ユーザー,
I want 自分でシグネチャを追加できる外部設定ファイル(例: `~/.config/mbyte/signatures.json`)を使いたい,
So that コードを書き換えずに新しいフォーマットを追加できる。
- 完了条件: 外部ファイルがあれば読み込み、無ければ内蔵デフォルトにフォールバックする。

---

### EPIC-2: diffプレビュー + 整合性チェック

**US-2.1**
As a ユーザー,
I want `replace`実行前に「検出された現在の署名 → 新しい署名」「変化するバイト数」「ファイルサイズの変化」のプレビューを見たい,
So that 実行前に何が変わるか理解した上で操作できる。
- 完了条件: デフォルトで実行前プレビューが表示され、`--yes`/`-y`で確認スキップ、`--dry-run`で書き込みなしの確認のみができる。

**US-2.2**
As a ユーザー,
I want 署名境界以降(ペイロード部分)のSHA-256ハッシュを操作前後で比較し、一致/不一致を表示したい,
So that `insert`や境界検出が正しい`replace`でペイロードが無傷であることを客観的に確認できる。
- 完了条件: 操作後に `payload hash: <before> -> <after> [MATCH/MISMATCH]` のような行が出力される。`insert`は常にMATCH、`--raw`で境界がズレる場合はMISMATCHと明示される。

**US-2.3**
As a ユーザー,
I want `--raw`で指定バイト数が検出済み署名長と異なる場合、失われる/残る具体的なバイト数を警告として表示したい,
So that 「気づかず壊した」事故を防げる。
- 完了条件: `--raw`使用時、検出署名長と指定長が異なれば差分バイト数を含む警告メッセージが出る。

---

### EPIC-3: バッチ処理

**US-3.1**
As a CTF問題作成者,
I want 1つのディレクトリ内の全ファイルに同じpreset/hexを一括適用したい,
So that ペイロードを1つずつ手動で処理する手間をなくせる。
- 完了条件: `mbyte insert --preset png ./payloads/ -o ./out/` のようにディレクトリを渡すと、中の全ファイルに適用され、`./out/`配下に同名で出力される。

**US-3.2**
As a ユーザー,
I want 1つのファイルに対して複数(または全)プリセットを一括適用し、各フォーマットのバリアントを一度に生成したい,
So that アップロードフィルタがどのシグネチャを通すか効率的に試せる。
- 完了条件: `mbyte insert --all-presets shell.php -o-dir ./variants/` で `variants/shell.php.png` `variants/shell.php.gif` 等がまとめて生成される。

**US-3.3**
As a ユーザー,
I want バッチ処理の結果を1つのサマリ(成功/失敗件数、各ファイルの検出フォーマット)として一覧表示したい,
So that 大量処理の結果を1件ずつ確認しなくて済む。
- 完了条件: バッチ実行後に表形式(ファイル名/適用preset/結果/検出フォーマット)のサマリが出力される。`--json`で機械可読形式も選べる。

---

### EPIC-4: polyglot構造検証

**US-4.1**
As a セキュリティ学習者,
I want 署名を偽装した後のファイルが、実際に対象フォーマットの標準パーサ(Goの`image/png`, `image/jpeg`, `image/gif`, `archive/zip`等)で正しく読み込めるかを確認したい,
So that 「先頭バイトだけの検証」と「実際にパースする検証」の違いを体感的に学べる。
- 完了条件: 操作後に `structural validity: PNG parser = FAIL (not a real PNG)` のような行が出力され、どのレベルの検証まで通過したか明示される。

**US-4.2**
As a ユーザー,
I want polyglotとして「シグネチャ一致」と「構造的妥当性」の両方の結果を1つのレポートとして見たい,
So that 自分の生成物がどのタイプのアップロードフィルタ(拡張子/MIME/マジックバイトのみ vs 実パース)を突破できるかの見積もりができる。
- 完了条件: `mbyte check <file>` サブコマンドで両方の結果(署名一致 / 構造妥当性)がまとめて表示される。

## MoSCoW優先度表

| ID | User Story | MoSCoW | 理由 |
|---|---|---|---|
| US-0.1 | core.pyのGo移植 | **Must** | 他の全機能の土台。これが無いと何も始まらない |
| US-0.2 | CLI層のGo移植 | **Must** | ユーザーが既存コマンドを使い続けられることが前提条件 |
| US-0.3 | テスト移植 | **Must** | リグレッション防止。移植作業自体の正しさを保証する唯一の手段 |
| US-2.2 | ペイロードハッシュ比較 | **Must** | 「壊れていないこと」を客観的に保証する、ツールの信頼性の核。実装コストも低い |
| US-1.1 | 検出対応フォーマットのプリセット化 | **Must** | 現状の非対称を解消する直接的な修正。実装コストが低く効果が大きい |
| US-2.1 | 実行前diffプレビュー | **Should** | 安全性向上に重要だが、US-2.2があれば実害は限定的。UX改善の位置づけ |
| US-1.2 | シグネチャ定義の一本化 | **Should** | US-1.1の副産物として同時にやるべきだが、優先度としてはリファクタリング |
| US-4.1 | polyglot構造検証(単体) | **Should** | 差別化効果は大きいが、フォーマットごとに実装量が増える。まず主要フォーマット(PNG/JPEG/GIF/ZIP)から |
| US-3.1 | ディレクトリ一括適用 | **Should** | 実用上の効率化。無くても困らないが、あると明確に便利 |
| US-2.3 | `--raw`差分警告 | **Could** | 既にUS-2.2のハッシュ比較で事実上カバーされるため、追加の価値は小さい |
| US-3.2 | 全プリセット一括生成(fan-out) | **Could** | 便利だが、US-3.1ができればシェルの`for`ループでも代替可能 |
| US-3.3 | バッチ結果サマリ/JSON出力 | **Could** | バッチ処理自体(US-3.1)が先。見やすさの改善は後回しでよい |
| US-1.3 | シグネチャ外部設定ファイル | **Could** | 拡張性は高いが、今のユーザー数・用途では内蔵リストで十分 |
| US-4.2 | `mbyte check`統合レポート | **Could** | US-4.1の結果を整形するだけなので、US-4.1の後に軽く追加できる |
| (将来) | アップロードエンドポイントへの実送信テスト | **Won't (this time)** | ネットワーク越しの診断ツール化は別フェーズ。まずローカル操作の完成度を上げる |
| (将来) | GUI化 | **Won't (this time)** | CLIツールとしての完成度を優先。GUIは需要が出てから検討 |

## 推奨実装順序

1. EPIC-0(Go移植: US-0.1 → US-0.2 → US-0.3) — 土台
2. US-1.1 + US-1.2(プリセット拡充・一本化) — 低コスト高効果
3. US-2.2(ペイロードハッシュ比較) — ツールの信頼性の核
4. US-2.1(diffプレビュー) — US-2.2の上に薄く乗せられる
5. US-4.1(polyglot構造検証、PNG/JPEG/GIF/ZIPから) — Go移植の最大のメリットを活かす
6. US-3.1(ディレクトリ一括適用)
7. Could群は余力があれば順次
